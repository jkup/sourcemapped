# RM-04: offline bounded sampling investigation

Investigated **2026-10-10** against scanner source revision `c55923a` (the committed parent of this investigation), with Node **26.10.0** and npm **11.19.1**. This is a controlled synthetic experiment, not a refreshed public-site study, user research, adoption evidence, or an estimate of live-site prevalence. [Historical evaluation](evaluation-2026-10-10.md) remains unchanged.

## Method and reproduction

Exact snapshot reproduction requires the [recorded study checkout](https://github.com/jkup/sourcemapped/tree/6dffa28e4ca6e182db1f043145446875a984fe7e). Later scanner revisions can add metadata; do not overwrite this historical snapshot to make a current-checkout comparison pass.

```sh
npm run build
node scripts/sampling-study.mjs > /tmp/sampling-study.json
cmp research/sampling-2026-10-10.json /tmp/sampling-study.json
```

The [small harness](../scripts/sampling-study.mjs) creates five pages, each with six unique static references: five scripts and one module preload. Synthetic maps contain one source path and no embedded source text. All responses are native `Response` objects supplied through injected `fetchImpl`; no network fallback, server, external site, original-source retrieval, or new dependency is involved. The [saved metadata](sampling-2026-10-10.json) includes selected URLs, request traces/statuses/bytes, checked bundle relationships, and separate exclusion counts. It is a study-specific format, **not** the production JSON report contract.

Four precisely defined policies operate on the production parser's deduplicated document-order list:

- **D2:** first two references, the current selection algorithm with a smaller research limit.
- **D4:** first four references, testing an explicit larger asset limit.
- **O2:** retain only URLs whose `URL.origin` equals the page's origin, then first two. This is exact scheme/host/port equality, not registrable-domain matching or proof of ownership. It compares advertised URLs before asset redirects. Calling it “first-party” would overstate what it knows.
- **P2:** retain URLs starting with the fixture's explicitly declared absolute URL prefix, then first two. Prefixes end with `/` and are case-sensitive literal matches on resolved URLs; they represent an operator choosing a known application directory, not automatic inference. The CDN case explicitly chooses its CDN prefix. This is only a research policy, not proposed CLI syntax.

The harness passes selected references as synthetic HTML to the unchanged scanner. Each scan still has one shared request/byte/time budget and map cache. It separately retains original discovery and policy exclusions because filtered HTML cannot provide those counts. It pads every synthetic page to 4,096 ASCII bytes, so page byte costs remain equal. For D2/D4 it additionally scans the original full page and asserts exact request evidence and selected-bundle equality, plus skipped-count agreement. This checks that the selection adapter reproduces current document-order behavior on these fixtures. It does not test a production filtering implementation.

Only `maxScripts`, concurrency, and the budget-control request cap are overridden. Concurrency is one for reproducible traces; all other limits come from [the scanner defaults](../src/network.ts). The `shared-and-failed` case has seven total request attempts available. Other cases use the current default request cap. The tiny asset limits make ordering effects inspectable; results do not predict the effect of changing the actual default of 24 to another value.

## Results

Each cell is **HTTP attempts / checked relationships / unavailable advertised maps / skipped references**. Attempts include the HTML request, failed requests, and redirects. “Checked” means the implemented checks passed, not debugging correctness or generated-code coverage. Shared maps count once per bundle relationship but only once per actual retrieval.

| Synthetic case | D2 | D4 | O2 | P2 |
| --- | --- | --- | --- | --- |
| Late application maps, early cross-origin scripts without references | 3 / 0 / 0 / 4 | 7 / 2 / 0 / 2 | 5 / 2 / 0 / 4 | 5 / 2 / 0 / 4 |
| Early CDN application maps, same-origin shell without references | 5 / 2 / 0 / 4 | 7 / 2 / 0 / 2 | 3 / 0 / 0 / 4 | 5 / 2 / 0 / 4 |
| Early same-origin vendor maps, application directory without references | 5 / 2 / 0 / 4 | 7 / 2 / 0 / 2 | 5 / 2 / 0 / 4 | 3 / 0 / 0 / 4 |
| Shared map, later 404 map and redirected script, seven-attempt cap | 4 / 2 / 0 / 4 | 7 / 2 / 1 / 3 | 4 / 2 / 0 / 4 | 4 / 2 / 0 / 4 |
| Only CDN assets, no origin or configured prefix match | 5 / 1 / 1 / 4 | 7 / 1 / 1 / 2 | 1 / 0 / 0 / 6 | 1 / 0 / 0 / 6 |

All cases discover six static references. The saved rows partition skipped counts into filter exclusions, eligible references past the asset limit, and selected references skipped by the runtime budget. For example, late-app O2 skips two by origin and two by the limit; P2 skips three by prefix and one by the limit. The budget D4 row skips two by the asset limit and one after a 302 consumes the last request slot. The 404 map consumes a slot and stays `unavailable`; two checked relationships share one fetched map. Empty filters still incur the page request and retain six excluded references in study evidence. No map is classified invalid, unsupported, or limited in these runs.

The fifth reference is always a preload and remains outside every selection in this study. Even D4's larger sample is incomplete. All asset lists and outcomes are intentionally constructed; aggregate success rates across them would have no population meaning.

## Selection bias and recommendation

Document order privileges early scripts and preloads, regardless of ownership or relevance. A larger limit reaches later assets but may spend requests on no-reference scripts, unavailable maps, or redirects before reaching the asset count. O2 favors deployment topology: it helps the late-app example and loses CDN application maps. It also retains same-origin vendor assets. P2 favors operator knowledge and naming conventions: it handles the configured CDN but intentionally loses mapped vendor code in early-maps. The no-match control shows why a filtered scan must report exclusions rather than suggest the page contained no static JavaScript.

**Keep the current default policy. The smallest useful proposed change is an opt-in positive-integer asset-limit CLI flag exposing the existing `maxScripts` setting, without increasing the shared request cap or other budgets.** D4 demonstrates both the potential gain and the cost of that choice, while requiring no automatic ownership heuristic or filter language. This is a recommendation for review, not implementation authorization or proof of user demand. Users can already target a known JavaScript URL directly; a multi-asset filter needs a concrete deployment workflow before its syntax and report compatibility are worth adding.

If accepted for a future implementation task, define the flag name/range and CLI argument errors; preserve default document order, effective limits, discovered/skipped totals, shared budgets and metadata-only output. Add deterministic CLI/scanner fixtures for an increased selection, no additional maps, and request exhaustion before the selected count; run the repository checks. Review ADR 0002 and report compatibility then. This investigation changes neither, so the accepted decision and production schema remain intact.

## Verification and limits

The build and harness completed successfully, all 20 rows reproduced byte-for-byte on a second invocation, and harness assertions cover the adapter baseline, discovery/inspection/skipped accounting, actual request traces, shared map cache, 404/redirect budget costs, and zero-match request count. `git diff --check` and relative links in changed documentation were checked. No production files or package configuration changed, so a full production test rerun was not required for this investigation; these checks are local and make no new remote CI claim.

This does not cover real ownership relationships, redirects of the page, base tags, duplicate discovery, concurrent request races, byte/time exhaustion, rate limits, dynamic imports, lazy execution, or owner preferences. Existing scanner tests cover several underlying mechanics, but this experiment supplies no new evidence for those scenarios. The recommendation is therefore about providing explicit control with limited complexity, not about proving a superior universal sampling strategy.
